# Сервер 40+ ядер: план и инструменты (02.11.2026)

**Цель недели (пользователь):** понять, как вычислительная мощь влияет на глубину перебора, как согласуются перебор и оценка при углублении, и сделать хороший эталон для 10 позиций набора v4. Память сервера — около 300 ГБ.

## 1. Параллельный перебор (`--threads N`)

Селективный луч до 02.11.2026 работал в один поток. Профиль (g7_02b, глубина 3): около 85–90% времени — ранжирование кандидатов в узлах (сотни независимых оценок, луч оставляет 8), остальное — рекурсия, порождение перемещений, листья.

**Параллельные оценки** (по умолчанию при `threads > 1`): оценки кандидатов узла — пакет независимых заданий; пул из `N − 1` помощников и основного потока разбирает пакет. Кэш статики, кэш гонки и кэш значений листа общие для всех потоков (seqlock на атомарных словах: рваное чтение — промах, занятая запись — не пишется). Пакеты: ранжирование шагов перемещений, состояния перемещений с предпросмотром End Turn, решения узла, подробная оценка короткого списка разнообразного луча, листья на глубине 1 (заранее, до рекурсии). Пакет меньше 8 заданий считается в своём потоке.

- **Значения, ход и число раскрытий не зависят от числа потоков** — меняется только время (проверено на 10 позициях, глубина 3, 1 и 2 потока).
- Ключ кэша таблицы эпизода включает нижний порог (результат «не выше порога» не переносится на другой порог) — иначе результат зависел бы от порядка вычислений.

**Деление корня** (`--root-split`, опыт): первое решение корня отдельно, остальные параллельно. Предел ускорения на 10 позициях — 1,2–2,8 раза при любом числе ядер (решения корня неравны по стоимости); оставлено как вариант.

**Доля параллельной работы** (`--profile-root`: время в пакетах ≥ 8 заданий при одном потоке) на 10 позициях при глубине 3 — P = 0,74–0,90; закон Амдала: ×8 — 2,9–4,8, ×16 — 3,3–6,5, ×40 — 3,6–8,4. Пакеты в среднем по 50–60 заданий, ~1 мс: при 40 потоках синхронизация станет заметной, фактическое ускорение покажет сервер.

**Два ядра (облако):** g7_02b глубина 3 — 19,5 → 12,0 с (деление корня — 15,3 с).

## 2. Пакет и запуск (02.11.2026, вечер)

Пакет `build/server_package/soccer_server_20261102.tgz` (папка `soccer_server/`): `src/`, `tests/`, `tools/`, `build_linux.sh`, `run_server.sh`, `README_SERVER.md`, этот план. Сервер (`lscpu` пользователя, 03.11.2026): AMD EPYC 7763 (64 ядра / 128 потоков, до 3,5 ГГц), включены 40 логических процессоров, из них 5 пар на общих ядрах — около 35 физических; один узел NUMA, L3 256 МБ (8 блоков по 32 МБ); ~300 ГБ памяти (поиск — ~0,3 ГБ на процесс). Скрипты считают ядра по маске процесса и `lscpu` (`os.cpu_count()` дал бы 128).

`./run_server.sh smoke` (несколько минут, всё в малом виде), затем `./run_server.sh all` в `tmux` или под `nohup`. Этапы: `info build scaling calib curves ladder consistency candidates verify report pack`; каждый продолжается с места остановки (строки CSV пишутся сразу, повторный запуск пропускает готовые); у каждого поиска тайм-аут, строка `timeout` в CSV. Результаты — `results/`, архив — этап `pack`.

Проверено (облако, 2 ядра, g++ 13): тесты 2 865 / 19 756 / 393 625 / 1 605, 0 ошибок; `-pkr-` при 1 и 2 потоках — тот же ход, значение и раскрытия на 10 позициях при глубине 2 и 3; ThreadSanitizer (`-pkr-`, `-pkr-etm-`, 4 потока) — чисто; `smoke` проходит за 4 мин.

## 3. Что мерить (`tools/server/bench.py`, бот по умолчанию `-pkr-`)

1. **Масштабирование** (`scaling`): глубина 3 и 4, потоки 1, 2, 4, 8, 16, 24, 32, физические, логические — время, ускорение, совпадение хода, значения и раскрытий (`same`).
2. **Калибровка** (`calib`): одни и те же однопоточные поиски глубины 3 по одному и по 34 / 40 сразу. Замедление под нагрузкой (частота, память, гиперпоточность) — поправка к кривым; 34 против 40 — даёт ли гиперпоточность пропускную способность.
3. **Глубина от времени** (`curves`): 30…3840 с, один поток, 34 процесса — какую глубину даёт время и меняется ли ход. Время × ускорение `scaling` = что даст мощность при игре.
4. **Лестница углубления** (`ladder`): d1…d6 из позиции и после хода бота (`suite_moves.txt`, соперник в корне), глубина за глубиной; не уложилась в тайм-аут — глубже не идёт; свободные ядра отдаются поискам потоками (значения от числа потоков не зависят). Смотреть: |V(d+2) − V(d)|, колебание по чётности, асимметрию корня, устойчивость хода.

## 4. Эталон для 10 позиций (`tools/server/reference.py`)

1. `candidates`: ходы `suite_moves.txt`, ходы пользователя (`user_moves.txt`), планы из `curves` и `ladder`, решения корня поиска ширины 16 глубины 3 (`--root-moves`), каждое досчитанное ботом. Кандидат обрезается после первого случайного действия (пас, удар, отбор): продолжение зависит от исхода, его выбирает проверяющий поиск. Кандидаты с одинаковыми итоговыми состояниями сливаются.
2. `verify`: из каждого исхода кандидата — поиск бота `--width W --turn-depth D` без лимита времени, по ядру на поиск; уровни `8x3, 8x4, 16x4, 8x5, 32x4, 16x5, 8x6` (дешёвые первыми). Значение кандидата для стороны хода = Σ p·значение исхода (гол = 1). Исходы реже `--min-p` = 0,02 (рикошеты удара, касания паса) считаются только на первом уровне.
3. `report`: таблица «кандидат × уровень» с рангами, устоялся ли порядок трёх лучших между двумя последними уровнями, ошибка кандидата = лучший − он на последнем уровне. Ошибка хода бота — по строке его источника.
4. Маленькие эпизоды у ворот (2 в 1, 1 в 0): точный перебор только по участникам (`goal-team-moves --frozen MASK --shot-only`) и таблица эпизода — отдельно, вручную.
5. Оценки пользователя — отдельной колонкой; расхождения разбираются.

**Ширина не монотонна:** g7_30b, глубина 2 — ширина 4: 0,697, 8: 0,774, 16: 0,708 (широкий луч видит и больше ответов защиты); раскрытий при ширине 16 в ~18 раз больше, чем при 8. Поэтому эталон — по нескольким уровням, а не «самый широкий».

## 5. Статика против перебора на глубине (`tools/server/consistency.py`, этап `consistency`)

Вопрос пользователя (03.11.2026): насколько хорошо перебор согласуется со статической оценкой на большой глубине.

1. `sample`: начала ходов команды из записанных партий (`ssbot positions`, 78 партий, ~1150 различных позиций; каждая 2-я), плюс 10 позиций v4; поровну по классам «кто ходит × у кого мяч (белые / чёрные / свободный)», до 600.
2. `static`: лист так, как его оценивает поиск (как есть и после конца хода), статика, составляющие `goal-static` (attack, direct-pass, lead-pass, keep, counter), вид эпизода (`attack-episode`: нет / общий / 1 в 0 / 2 в 1).
3. `depths`: V(d) при d = 1–4 для всех, 5 — для 100, 6 — для 30 (поровну по классам); глубина за глубиной.
4. `horizon`: главная линия глубины 3 повторными поисками (план поиска глубины d, затем оставшейся глубины из полученной позиции; после паса — исход «мяч прошёл», линия с ударом не учитывается); в её листе — статика против поиска глубины 1–3 из листа. Поиск выбирает листья, где оценка ошибается в его пользу: знак и размер «статика − поиск» для стороны в корне — это ошибка оценки там, куда ведёт перебор.
5. `report` (`cons_report.txt`): по классам и глубинам — смещение и средняя ошибка V(d) − статика, корреляции Пирсона и Спирмена; V(d+1) − V(d) для стороны хода (чётность — право хода); ошибка в листе линии; связь V(dmax) − статика с составляющими и видом эпизода — только диагностика (где ошибается алгоритм), не подгонка весов.

Проба в облаке (40 позиций, d1–d2, линии глубины 2): корреляция статики с V(d) 0,83–0,85; в листе линии статика ниже поиска из листа для стороны в корне (−0,07 на 7 линиях) — выборка мала, вывод только на сервере.

Открыто (решение пользователя): калибровка статики как вероятности гола по сотням быстрых партий бот против бота.

Изменение бота принимается по уменьшению суммарной ошибки на наборе (`AGENTS.md`).
